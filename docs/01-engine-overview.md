# 01. Engine Overview

Read this file first. It defines the terminology used by every other document.

## What VoxelCore is

VoxelCore (repo: <https://github.com/MihailRis/voxelcore>) is an open-source voxel
game engine written in C++ with Lua scripting. It ships as an engine binary
(`VoxelEngine` / `VoxelCore`) plus a built-in content pack `base` in `res/content/`.

Game content is **declarative**: blocks, items and most other content are plain
JSON files inside *content packs*. Lua scripts are optional and add behavior on
top of JSON declarations. DO design content as JSON first; add Lua only when the
JSON properties are not enough.

## Core terminology

| Term            | Meaning                                                                 |
| --------------- | ----------------------------------------------------------------------- |
| Content pack    | A folder containing `package.json` and optional content subfolders.     |
| Pack ID         | The unique identifier declared in `package.json` (`"id"` field).        |
| Block           | A voxel type occupying grid cells in the world (stone, water, torch...).|
| Item            | An inventory object. Every block automatically gets a corresponding item.|
| Content source  | A filesystem path the engine scans for packs (see 02-pack-structure).   |
| Mount point     | Internal virtual filesystem entry; each pack gets one named after its ID.|
| Atlas           | A texture collection. Atlases `blocks` and `items` are built from PNGs in the pack's `textures/blocks/` and `textures/items/`. |
| Caption         | Human-readable display name of a block/item shown in the inventory UI.  |

## Namespaced IDs

All content is addressed as `pack_id:content_name` — e.g. `base:dirt`,
`base:grass_block`, `kompot:ui`.

Rules for IDs (`[VERIFIED]`, identical rules for packs, blocks and items):

- Allowed characters: Latin letters `a-z` `A-Z`, digits `0-9`, underscore `_`.
- MUST NOT start with a digit.
- Length MUST be 2..24 characters inclusive.
- IDs are case-sensitive as written, but DO use lowercase for new content;
  all real packs do.

The special suffix `.item` denotes the item auto-generated for a block:
`base:stone.item` is the item form of block `base:stone`. `[VERIFIED]`
You only need the `.item` form when referencing a block's generated item
explicitly (e.g. in loot tables).

## Reserved names

Pack IDs collide with mount point names, so these are reserved / unavailable for
pack IDs: `res`, `user`, `world`, `project`, `config`, `core`. `core` is an
additional engine-internal pseudo-pack that provides built-in content (e.g. the
empty item `core:empty`). Engine-level tags are namespaced `core:*` (e.g. blocks
carry `"tags": ["core:liquid"]`); packs add their own namespaced tags (the stock
pack tags its ore `base:ore`). `[OBSERVED]`

DO NOT use any of these as pack IDs.

## What a content pack can contain

A minimal pack is **just `package.json`** and it is valid — confirmed
first-hand, nothing else is required. Everything else is optional subfolders:

- `blocks/` — block definitions (JSON) — covered in 03-blocks.md
- `items/` — item definitions (JSON) — covered in 04-items.md
- `textures/` — PNG assets (`textures/blocks/`, `textures/items/`, ...) — covered
  in 05-textures-and-assets.md
- `block_materials/` — interaction material definitions (JSON) — covered in
  05-textures-and-assets.md
- `texts/` — localization files — covered in 05-textures-and-assets.md
- `config/` — TOML config (`defaults.toml`, `bindings.toml`, `user-props.toml`)
  — covered in 02-pack-structure.md
- `package.json`, `icon.png`, `preload.json` — covered in 02-pack-structure.md
- `content.json` — auto-generated by the engine. NEVER create or edit it by hand.
- Excluded topics (defined but NOT documented in this guide): `entities/`,
  `skeletons/`, `models/`, `sounds/`, `shaders/`, `fonts/`, `layouts/`,
  `generators/`, `scripts/`, `modules/`, `presets/`, `animations/`. See
  `docs/stubs/` before assuming anything about them.

## How loading works (mental model)

1. The engine scans **content sources** (folders) for subdirectories containing
   a `package.json`.
2. Each discovered pack is registered by the `"id"` from its `package.json`;
   the folder name itself is not the identity, and in real packs it almost
   never equals the ID. `[OBSERVED: pack folder
   kompot_0f9103ff-1.2.2 ships id "kompot" and works]`
3. Dependencies declared in `package.json` are resolved; missing hard
   dependencies fail the load.
4. All enabled packs' content folders (`blocks/`, `items/`, ...) are read and
   every definition is registered into a global, namespaced registry
   (`pack_id:name`).
5. The engine writes/updates each pack's `content.json` (registry index used to
   keep world saves stable across content changes).
6. At runtime, blocks/items referenced anywhere (JSON or Lua) use the
   `pack_id:name` string form; internally they become numeric runtime indices.

Consequences you MUST respect:

- AVOIDs nothing here: removing/renaming content that worlds already contain is
  handled through `content.json` conversion, but renaming IDs still breaks
  references in JSON/Lua and localization. Treat published IDs as immutable.
- The engine does not currently compare pack versions when resolving duplicate
  packs across sources — highest-priority source simply wins. `[DOC]`

## Engine version policy of this guide

This guide is written against the `main` branch state of October 2026 (base pack
version 0.32). It is intentionally not pinned to a commit. If the engine changes
JSON formats, the stock pack `res/content/base/` in the engine repo is always the
authoritative example set — DO re-check it when in doubt.
